# Замер поиска без модели (retrieval-only)

## Зачем

`context_recall` (0,833 на `eval/real`, 31.10.2026) сейчас считается только полным замером: проверка с моделью,
долго и платно. Для подбора настроек поиска (идеи 1–6) нужен быстрый замер того же показателя без модели:
секунды на прогон, без токенов. Плюс разбор каждого промаха — почему фрагмент не попал к модели.

## Как сейчас считается

- Риск в `expected.yaml`: `rule`, `present: true`, `quote_contains` (`eval/run.py:133-138`).
- `context_recall`: `quote_contains` найдена в тексте фрагментов, которые видела модель
  (`details["context"]` — список ID, `eval/run.py:114-140`, `llm_check.py:65-66`).
- Запрос поиска правила: `" ".join([*search_hints, question])` + подсказки полнотекста `search_hints`
  (`llm_check.py:115`); `make_retriever` → `HybridSearch.search` (RRF, `PER_METHOD = 20`,
  `top = max(8, 3 × число правил)`) → `expand` (бюджет `PROMPT_BUDGET_TOKENS`) (`orchestrator.py:318-336`).
- Ранги не сохраняются: после прогона не видно, был ли фрагмент в выдаче, но отрезан бюджетом.

## Решение

Скрипт `backend/svetofor/eval/retrieval.py` (+ цель `make eval-retrieval SET=real`):

1. **Загрузка пакета один раз**: тот же путь, что у `eval/run.py` (`create_check` → `prepare_package` →
   `process_document` → `embed_chunks`), классификация документов — как в обычном замере (с моделью, ответы
   ложатся в кэш БД; повторно токены не тратятся). Пакет, уже загруженный в БД, не загружается снова.
2. **Поиск по каждому риску** `present: true` с `quote_contains` у llm_check-правила: запрос строится той же
   функцией, что в `llm_check.py` (вынести построение `SearchRequest` в общую функцию — без смены поведения),
   группа правил — как в движке (`max_rules_per_call`).
3. **Итог по риску**: найден ли `quote_contains` в фрагментах после `expand` (= `context_recall`), место
   фрагмента в RRF до обрезки (ранг вектора / полнотекста), причина промаха:
   - `cut_by_budget` — был в выдаче RRF, не влез в бюджет;
   - `not_ranked` — нет в первых `PER_METHOD` ни одного способа;
   - `wrong_doc_type` — фрагмент в документе типа, которого нет в `applies_to`;
   - `not_in_chunks` — фразы нет ни в одном фрагменте пакета (нарезка / OCR / ошибка разметки).
4. **Отчёт** `eval/results/<дата>_retrieval_<set>.md`: recall, таблица промахов с причиной, параметры прогона.
   Не коммитить без просьбы владельца.
5. **Параметры через аргументы** (`--per-method`, `--top`, `--budget`), чтобы подбирать без правки кода.

### Не меняется

- Поведение проверки, промпты, правила, кассета модели.
- Полный замер `make eval` — остаётся главным; этот — только для поиска.

## Критерии приёмки

1. `make eval-retrieval SET=real` на 6 пакетах проходит без вызовов модели (кроме классификации при первой
   загрузке) и без Celery/Redis.
2. Recall этого замера совпадает с `context_recall` полного замера 31.10.2026 (0,833) в пределах ±0,03 —
   иначе разобрать, почему расходятся.
3. У каждого промаха указана одна из четырёх причин.
4. Повторный прогон (пакеты уже в БД) — меньше 1 минуты.
5. Юнит-тесты на разбор причин (без БД) и на общую функцию построения запроса; все тесты и линтеры зелёные.

## План

1. Общая функция построения запросов из правил (`llm_check.py` → её же вызывает скрипт) + тест.
2. Скрипт: загрузка пакета / поиск / причины / отчёт. Тесты разбора причин.
3. Цель в `Makefile`.
4. Прогон на `eval/real` в Docker, сверка с 0,833.

## Инфраструктура и риски

- Нужны контейнеры `db` (PostgreSQL + pgvector) и `tei` (~1–1,5 ГБ ОЗУ), сборка образа `api`
  (LibreOffice, Tesseract — несколько ГБ, данные Docker на D:).
- Слабая машина: после прогона `docker compose down`, выход из Docker Desktop, `wsl --shutdown`.
